# P7 Planning Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver roadmap phase P7: schedules with a business-day recurrence engine, occurrences that ledger transactions realize, subscriptions with price changes, pauses and ends, budgets with rollover, goals, account projections and committed amounts (S27–S29, S60–S63).

**Architecture:** A new module `internal/planning` (`planning.go` → `internal/domain` → `internal/app` → `internal/adapter/{postgres,httpapi}`) owns the `planning_` tables. The recurrence engine is pure domain code over a business-day set that the app loads from `marketdata` (`br_banking`). Occurrences are stored rows generated up to a 12-month horizon; a scheduler in the application process extends the horizon. Planning reacts to the ledger transaction events through the outbox (ADR 006) and reads the ledger only through `ledger.Module` methods (ADR 002).

**Tech Stack:** As P6. New dependency: none. New PostgreSQL extension: `btree_gist` (contrib, shipped with the `postgres:18` image) for the pause exclusion constraint of 7.3.

**Spec:** `docs/domain/` chapters 1 (G2, G4, T01–T03, T06, T09), 2 (2.6, 2.10), 3 (F7), 4 (4.3.4), 5 (5.3, 5.7 occurrence generator and matcher), 6 (S06 committed amount, S27–S29), 7 (7.3 planning tables, 7.5 occurrence index, 7.6 I07 and I08); ADR 002, ADR 005, ADR 006, ADR 007; this plan's "Spec amendments" and "Scenarios".

## Spec amendments (approved with this plan)

| ID | Amendment | Reason |
|---|---|---|
| A46 | A schedule template is one balance account (`account_id`), one counterpart (`counterpart_id`), an optional payee and a description of 1–200 characters. Counterpart by kind: `bill` and `subscription` an expense category, `income` an income category, `transfer` and `savings` an asset or liability balance account other than `account_id`. Money leaves `account_id` for every kind except `income`. The template is stored in columns with composite foreign keys to `ledger_account` and `ledger_payee`, not in `template jsonb` (7.3). | One counterpart covers S27–S29; columns keep user isolation in the database (7.1). |
| A47 | In P7 both template accounts and the schedule amount are in the user's base currency; another currency returns 422 `currency_unsupported` on `account_id` or `counterpart_id`. Budgets and goals follow the same rule. P8 amendment A72 lifts it. | Multi-currency weights arrive with P8. |
| A48 | Recurrence: `daily` every `interval` days from `start`; `weekly` every `interval` weeks on the weekday of `start`; `monthly` every `interval` months with exactly one selector (`day_of_month` 1–31 or −1, `weekday` + `ordinal` 1–5 or −1, `business_day_ordinal` 1–23 or −1); `yearly` every `interval` years on the month and day of `start`. A day that does not exist resolves to the last day of the month (T02); a missing Nth weekday or Nth business day resolves to the last one of the month. `adjustment` (default `none`) applies after the selector and never to `business_day_ordinal`. Business days come from calendar `br_banking`. `until` is inclusive; `count` limits the dates of the rule, counted from `start`. Dates before `start` are never produced. | 5.3 lists the fields without the weekly, yearly and fallback semantics. |
| A49 | Sequence numbers count the dates of the schedule from 1. A terms version effective from date E produces the dates of its own rule in [E, next version's E); its first sequence follows the last sequence of the earlier versions before E. A terms change that gives only an amount copies the previous rule, `start` included. Occurrences are generated with `expected_on` up to the horizon (today + 12 months); generation is idempotent by `(schedule_id, sequence)`. | 5.3 "sequence numbers never change when terms change". |
| A50 | Stored occurrence states are `expected`, `realized` and `skipped`; `overdue` is derived on read (state `expected` and today > `expected_on` + `grace_days`). `OccurrenceOverdue` and `BudgetExceeded` (4.3.4) are not published in P7: no module consumes them. | Derived state needs no clock job; an event without a consumer is unverifiable. |
| A51 | Realization: on `ledger.transaction_recorded.v1`, `…_corrected.v1`, `…_categorized.v1` and `…_voided.v1`, Planning re-evaluates a transaction whose `account_ids` include a template account of one of the user's schedules. A non-voided transaction matches an expected occurrence when it has a posting on `account_id` with the kind's sign whose absolute amount A satisfies \|A − E\| × 10000 ≤ E × `match_tolerance_bp` (default 1000), a posting on `counterpart_id`, the template payee when the template has one, and a date within `expected_on` ± 7 days. Among matches the closest date wins, then the lower sequence. An automatic realization that stops matching, and any realization of a voided transaction, returns the occurrence to `expected`. `POST /occurrences/{id}/realize` links a chosen transaction (`realized_by = manual`), which re-evaluation never releases; `POST /occurrences/{id}/unrealize` releases it. | F7 "match … within the window" names no window; imports reach their category after recording (A19). |
| A52 | Skip and move act only on an `expected` occurrence (409 `occurrence_closed` otherwise). A moved occurrence keeps its sequence, stores `moved_from` and is never regenerated. A terms change, a pause and an end delete and regenerate only `expected` occurrences that were not moved, from the effective date on. A pause covers `[from, to]` inclusive and suppresses dates in it; pauses of one schedule never overlap (409 `pause_overlap`). `POST /schedules/{id}/end` with `from` produces no date on or after `from`; terms and pauses dated on or after `ends_on` return 409 `schedule_ended`. | S29; T03, T09. |
| A53 | A scheduler ticks at start and every hour: it extends every schedule whose `generated_until` is before today + 12 months. | The horizon moves with the clock. |
| A54 | Budget: one per category (409 `budget_exists`), monthly, effective-dated amounts by first day of month, `rollover` flag. Spent in a month = the sum of the weights of the non-voided postings in the category subtree with `booked_on` in the month (accrual view), negated for income categories. Available = planned + carried − spent; carried = the previous month's available when `rollover` is true, from the first effective month, and may be negative. | 5.3 Budget, rollover sign unspecified. |
| A55 | Goal: name 1–60, target, due date, one or more balance accounts. Progress at today: current = sum of booked balances of the accounts, remaining = max(target − current, 0), `progress_bp` = min(⌊current × 10000 ÷ target⌋, 10000). | 2.10 Goal. |
| A56 | Projection of a balance account to date D (today < D ≤ today + 12 months): the opening is the booked balance at today; each point is an expected occurrence touching the account (as `account_id` or `counterpart_id`, overdue ones dated today) with expected date in [today, D], ordered by date then signed amount ascending, with the running balance; the closing is the booked balance at D, which includes transactions already recorded with future dates, plus the sum of the points. Card statements enter only through a schedule of kind `transfer` to the card account. | 2.6 Projection; no payment account per card exists in the model. |
| A57 | Committed amount of month M (`GET /commitments?month=`): `installments` = the sum over the user's card accounts of the ledger commitment of M (installments billed on statement M while it is open, P2); `occurrences` = the sum of expected occurrences of kinds `bill`, `subscription` and `savings` with expected date in M; `total` = both. Kinds `income` and `transfer` are excluded, so a card payment schedule does not count the installments twice. | 2.10 Committed amount. |

## Global Constraints

- All earlier constraints apply.
- Planning reads the ledger only through `ledger.Module` methods; its SQL touches only `planning_` tables, except foreign keys to `ledger_account`, `ledger_payee` and `ledger_transaction` (7.1, ADR 002).
- Defaults: `match_tolerance_bp` 1000, `grace_days` 3, horizon 12 months, realization window ± 7 days, calendar `marketdata.CalendarBRBanking`.
- Occurrence ranges in requests span at most 366 days (422 `validation_failed` on `to`); lists of schedules, budgets and goals paginate by cursor (ADR 007, C8); occurrences of a requested range return without a cursor.
- Tests fix the date with `apitest.Today`; the scheduler is exercised through `App.Planning.Tick`, never through a ticker.

## Review Focus

1. A terms change effective between occurrences while earlier ones are realized, skipped or moved keeps their sequence and state and creates no duplicate sequence (Task 4).
2. A transaction that fits two expected occurrences (overlapping ± 7-day windows of a weekly schedule, or two schedules with the same accounts) realizes exactly one; a redelivered event changes nothing (Task 3).
3. A month without the Nth business day (February 2027 with Carnival) or a `modified_following` day 31 that would cross into the next month lands on the dates of A48 (Task 1).
4. Voiding the realizing transaction returns the occurrence to `expected`, shown `overdue` after the grace period, and the next matching transaction realizes it (Task 3).
5. Two ticks on the same day, a tick after a restart and a schedule with `count` across several horizon extensions create no extra occurrence and stop exactly at `count` (Task 4).

```go
package domain // Schedules, occurrences, budgets and goals of the Planning context (docs/domain, 5.3).

type Frequency string // daily, weekly, monthly, yearly
type Rule struct {
	Frequency          Frequency
	Interval           int // ≥ 1
	DayOfMonth         int // 1–31, −1 last day, 0 unset
	Weekday            *time.Weekday
	Ordinal            int // 1–5, −1 last; with Weekday
	BusinessDayOrdinal int // 1–23, −1 last, 0 unset
	Adjustment         string // none, following, preceding, modified_following
	Start              time.Time
	Until              *time.Time // inclusive
	Count              int        // 0 unlimited
}
type BusinessDays interface{ IsBusinessDay(d time.Time) bool } // weekends and holidays
type Dated struct{ Sequence int; Date time.Time }
func (r Rule) Validate() error // *FieldError wrapping ErrValidation, field names as in the API (recurrence.day_of_month …)
func (r Rule) Dates(from, to time.Time, days BusinessDays) []Dated // dates in [from, to], sequence counted from Start
```
