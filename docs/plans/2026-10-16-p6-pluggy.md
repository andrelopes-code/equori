# P6 Pluggy Ingestion Implementation Plan

**Goal:** Deliver roadmap phase P6: synchronize the owner's accounts from Pluggy through Meu Pluggy into the ledger, with encrypted credentials (N15), account mapping, repeatable syncs (SC2), card statement hints, installment plans, source categories and balance assertions, so that a synchronized real account reconciles (SC1).

**Architecture:** Ingestion gains a Pluggy anti-corruption layer (`ingestion/internal/pluggy`) that turns Pluggy items, accounts, bills and transactions into Ingestion's `NormalizedRecord`. A sync run is one import batch per mapped account and reuses the P4 pipeline (deduplication, matching, classification, recording) with source `open_finance`. Credentials are sealed with AES-256-GCM under a key from the environment (ADR 008). A scheduler in the application process syncs connections whose Pluggy item has new data; equori never triggers Pluggy updates.

**Tech Stack:** As P5b. New dependency: none (`crypto/aes`, `crypto/cipher`, `net/http` of the standard library).

**Spec:** `docs/domain/` chapters 1 (G6, SC1, SC2), 3 (F4, F5 source category, F6), 4 (4.3.3), 5 (5.5), 7 (7.3), 8 (N15, N16, N17); ADR 002, ADR 003 ("Not covered"), ADR 006, ADR 007; Pluggy documentation (docs.pluggy.ai, read on 2026-10-16: authentication, items, accounts, `GET /v2/transactions`, bills, credit card installments, rate limits) and the Meu Pluggy guide (pluggy.ai/meu-pluggy); this plan's "Spec amendments" and "Scenarios".

## Spec amendments (approved with this plan)

| ID | Amendment | Reason |
|---|---|---|
| A33 | ADR 008: integration credentials are sealed with AES-256-GCM under `EQUORI_SECRET_KEY` (32 bytes, base64), with the table, user and row as associated data and a key version byte; `EQUORI_SECRET_KEY_PREVIOUS` opens values sealed with the previous key, and `equori secrets rotate` reseals them. Without a key, integration endpoints return 409 `integration_unavailable`. | N15 and ADR 003 "Not covered". |
| A34 | Credentials belong to an integration, not to the connection: `ingestion_integration (id, user_id, provider, name, credential_ciphertext)` holds one Pluggy client id and secret, and a user may have several (two Meu Pluggy accounts, or a paid plan beside them). `ingestion_connection` holds the integration, the item id, Pluggy status and sync state. An integration with connections cannot be deleted (409 `integration_in_use`). | One Pluggy application key reads every item of its application; more than five connections need a second application or the paid plan. |
| A35 | A connection lists the item's accounts as external accounts (type, subtype, name, last four digits of the number, currency). The owner maps each to one leaf balance account of the same currency and a compatible kind (`CHECKING_ACCOUNT` → checking, `SAVINGS_ACCOUNT` → savings or reserve, `CREDIT_CARD` → credit_card) with a sync start date, or ignores it. Only mapped accounts sync. | 5.5 AccountMapping; the owner chooses where data lands. |
| A36 | A sync of one mapped account is one import batch with source `open_finance`. The window starts at the mapping's start date on the first sync and 30 days before the last synced date afterwards, and ends today (America/Sao_Paulo). The deduplication key uses the Pluggy transaction id. A bank `PENDING` transaction is skipped. A record already stored is updated, not ignored, when Pluggy changed its status, bill or amount: the posting turns `cleared` on `POSTED` and moves to the bill's statement when it is not reconciled. | SC2 with Pluggy's mutable records (PENDING → POSTED, billId arrival). |
| A37 | Amounts are read from the JSON number text into minor units of the account currency, never through binary floating point; more decimals than the currency scale reject the record. Card amounts change sign. A foreign-currency line uses `amountInAccountCurrency`. A `date` at 00:00:00Z is that calendar date; any other instant is converted to America/Sao_Paulo. | Exact money (ADR 005). |
| A38 | A record whose Pluggy id is missing from a later window that covers its date becomes `withdrawn`: its posting link is released and its transaction stays. A transaction returned again with a new id then matches the released posting instead of duplicating it. | Pluggy deletes and recreates transactions. |
| A39 | Statement hint: a card line with `billId` is billed on the statement whose due date equals the bill's `dueDate`, otherwise on the reference month of that due date. | Billing follows the bank, not the configured cycle. |
| A40 | Installments: a card line with `installmentNumber` k of `totalInstallments` n belongs to an aggregator plan keyed by card, purchase date, n, installment amount and normalized description. The first line seen creates a ledger installment purchase of n installments with the issuer amount, first statement k − 1 months before the line's statement; every line links to its installment posting. A line whose amount differs from its installment goes to review. | Banks report installments in three patterns; one plan per purchase keeps committed amounts right. |
| A41 | Source category: Classification records each provider category seen (`classification_source_category`: provider, external id, name, count, mapped category). A mapped category decides the line when no rule does (method `source`, F5 precedence). | F5 "source category"; SC5 share of import data. |
| A42 | A bank account sync records a balance assertion from `balance` at the date of the item's `lastUpdatedAt` (America/Sao_Paulo) with source `open_finance`. Such assertions never record yield automatically: a difference is reported (F6 `DifferenceFound`). | Yield arrives as feed transactions (B04); a missing same-day line must not become yield. |
| A43 | A scheduler syncs every connection whose item `lastUpdatedAt` is later than its last sync, every `EQUORI_SYNC_INTERVAL` (default 1 hour); `POST /connections/{id}/sync` runs one now. A connection whose item is `LOGIN_ERROR`, `OUTDATED` or `WAITING_USER_INPUT` is not synced and shows the status. Two syncs of one account never overlap (P4 advisory lock). | Meu Pluggy updates items daily; equori only reads. |
| A45 | Each user of the instance has their own integrations, connections, mappings and API key cache (one per integration); a sync reads and writes only its user's rows. The same item id may be registered by two users, each importing into their own ledger. Under Meu Pluggy's free plan each person uses their own Meu Pluggy account and Dashboard application (connections of the same account holder only). | ADR 003: every business row belongs to one user; a family member is a second user. |
| A44 | Logs and problem details name connections and accounts by equori id only: no client secret, API key, item id, account number or Pluggy payload (N16). Outbound HTTP goes only to the configured Pluggy base URL (N17). | N16, N17. |

## Global Constraints

- All earlier constraints apply.
- Tests never contact Pluggy: `internal/ingestion/internal/pluggy/pluggytest` serves recorded-shape responses from Go values; the base URL is configuration (`EQUORI_PLUGGY_URL`, default `https://api.pluggy.ai`).
- HTTP client: 30 s timeout per request, at most 3 attempts on 429 and 5xx honoring `Retry-After` (capped at 60 s), context cancellation respected.
- The API key is cached in memory per user until 10 minutes before expiry; never stored.
- SC1 is checked by the owner with a real Meu Pluggy item following `docs/operations/pluggy.md`; the result is recorded in the closing checkpoint.

## Review Focus

1. Amounts with three decimals, very large amounts and amounts written in exponent notation (`1.5e2`) parse exactly or reject the record; `0.1 + 0.2` style values never lose a cent (Task 2).
2. A sync interrupted after some batches leaves the next sync complete and duplicate-free; two scheduler ticks and a manual sync on one account never run at the same time (Task 5).
3. A `POSTED` update for a posting already reconciled keeps the posting and its statement unchanged and records the difference on the record (Task 4).
4. Logs of a failed sync, a 401 from Pluggy and a rejected credential contain none of: client secret, API key, item id, account number (Task 3, Task 5).
5. An installment line whose plan was refunded or cancelled in the ledger goes to review instead of failing the batch (Task 6).

## Slice A (Tasks 1–3)

### Task 1: ADR 008 and sealed secrets (A33)

**Files:** `docs/adr/008-integration-credentials.md`, `internal/platform/secret/secret.go` and test, `internal/platform/config/config.go` (`EQUORI_SECRET_KEY`, `EQUORI_SECRET_KEY_PREVIOUS`) and test, `cmd/equori/main.go` (`secrets rotate`), `docs/operations/backup.md` (the key is not in the backup; losing it loses the credentials only).

```go
package secret // Seals integration credentials with AES-256-GCM (ADR 008).
type Box struct{ /* current and previous keys */ }
func New(current, previous []byte) (*Box, error) // 32-byte keys; previous may be nil
func (b *Box) Seal(plaintext, associated []byte) ([]byte, error) // version byte | nonce | ciphertext
func (b *Box) Open(sealed, associated []byte) ([]byte, error)    // ErrUnreadable on a wrong key, tampering or other associated data
func (b *Box) NeedsReseal(sealed []byte) bool
```

**Tests:** round trip; tampered byte, other associated data and unknown key fail with `ErrUnreadable`; previous key opens and `NeedsReseal` reports it; config rejects a key that is not 32 bytes of base64; rotate reseals every row (Task 3 table) in one transaction.

Commit `feat(platform): seal integration credentials`.

### Task 2: Pluggy client and normalization (A37, A39)

**Files:** `internal/ingestion/internal/pluggy/{client.go,model.go,amount.go,normalize.go}` and tests, `internal/ingestion/internal/pluggy/pluggytest/server.go`.

```go

func NewClient(baseURL string, hc *http.Client, clk Clock) *Client
func (c *Client) Session(ctx context.Context, clientID, clientSecret string) (*Session, error) // ErrUnauthorized on 401/403
```
